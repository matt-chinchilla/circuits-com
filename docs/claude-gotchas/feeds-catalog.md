# Distributor feeds, part identity & catalog writes — full gotcha histories

Moved verbatim from CLAUDE.md 2026-08-28 to cut per-session context cost. The
compressed rule (same bold key) lives in CLAUDE.md's Gotchas section; this file
holds the full story — evidence, measurements, dates, refuted hypotheses.
**Update BOTH files when a rule changes.**

- **Feed runs are SERVER-OWNED (2026-08-20)** — POST sync/import STARTS a run (daemon worker owns its own SessionLocal + provider; per-part commits) and returns an OBSERVER NDJSON stream; closing the stream DETACHES, never cancels. `GET /suppliers/{id}/feed-run` reattaches (full replay + live tail, `X-Feed-Run-Id`/`X-Feed-Run-Mode`); concurrent start = 409 `feed_run_already_active` — that guard is `_RUNS`, a module dict, so it only arbitrates **inside the api process**. The cross-process half landed 2026-08-23 as **`app/services/feed_lock.py`** (`supplier_feed_lock`, a Postgres advisory lock), taken by BOTH `_feed_run_worker` and `jobs/feed_import_daily._import_one` — without it an admin Import during the nightly sweep double-swept a supplier and `_save_import_cursor` (which rewrites the whole map from a run-start snapshot) discarded the loser's paging depth. **Advisory, not a lock row, precisely because Postgres frees it when the connection dies** — a row would survive a container restart mid-run and wedge that supplier's feed until a human noticed. It holds its OWN connection: locks are per-connection and a Session returns its connection to the pool at every commit. The key is `crc32` of the canonical UUID, never `hash()` (salted per process → the two containers would contend on different keys and the guard would be silently inert). A REFUSED caller must not unlock on exit; non-Postgres engines get a permissive no-op. The api side raises `FeedRunElsewhere` from inside the worker thread (the route has already answered) and **catches it BY NAME** to emit a plain `sync_finished` "stood down" — falling through to the generic handler filed a healthy nightly-sweep collision as "Import failed"/"import aborted" with zero counts, a red run describing a system working as designed. The nightly side likewise **must not `_stamp_run` a skipped supplier** (that column means "when did we last spend calls here"; claiming a run that never happened is how a supplier silently stops being imported) and counts it as `skipped_locked` in the summary. OPEN, deliberately deferred: the collision is discovered inside the worker thread AFTER the route returned 200, so the same condition answers 409 in-process and a stream event cross-process. The deeper fix is to acquire in `start_feed_run` and hand the connection to the worker — ~20 lines, but it changes the lifecycle of a shipped, heavily-tested feature. Guard: `test_feed_lock.py` (15, real Postgres); 20s bare-`\n` heartbeat + `proxy_read_timeout 300s` in all three nginx configs. Registry is IN-PROCESS (fine on today's single worker — multi-worker needs an activity_events fallback); container restart truncates a run (import_cursor makes the next resumable). Wire events byte-identical; `sync_event()` sole constructor. **Second click = PAUSE (d0de686)**: `POST /suppliers/{id}/feed-run/pause` sets `FeedRun._stop`; the worker WINDS DOWN at the next safe part (part in hand commits — every ending counter is a committed fact), emits a normal `sync_finished` with real counts + "paused — click again to resume" detail, and FREES the 409 slot immediately; import_cursor makes the next click a resume. Pausing nothing = 404 `no_feed_run`. UI: the ACTIVE run's QuickActions card becomes 'Pause sync'/'Pause import' via `serverRunMode` (`X-Feed-Run-Mode`); the other card stays disabled. Guard: `test_feed_run_durability.py` (incl. `TestPauseIsAClick`).

- **Distributor feed surface (2026-08-17/18)** — `app/services/part_feed/`: `registry.match_provider(supplier)` keys on WEBSITE domain fragment → (slug, provider class); keys resolve `get_feed_key(db, slug)` = `provider_credentials` DB row (Admin → Settings "Distributor feeds" card, write-only API, demo sees REDACTED) else env `MOUSER_API_KEY` (compose maps it from HOST var `MOUSER_SEARCH_API_KEY` — the host `.env`'s own `MOUSER_API_KEY` line is a DEAD Order-API key, never pass it through). Two streaming admin routes, one NDJSON event contract (**6-key counts** incl. `created` + `listing_added`; actions updated/media_filled/not_found/no_data/created/listing_added; `sync_event()` in importer.py is the ONLY event constructor): `POST /suppliers/{id}/sync` (1 call = 1 part refresh) and `POST /suppliers/{id}/import` (keyword search, 1 call ≈ 50 parts, `grow_catalog` thinnest-category-first, hard page caps). **THE TWO BUTTONS ARE DISJOINT, and the split is one question — does this supplier already list this part? (2026-08-24, owner-reported).** `sync_supplier_listings` selects exactly the parts where it does (an EXISTS on part_listings); `grow_catalog` takes exactly the complement, so every (part, supplier) pair belongs to one button and neither does the other's work. Import used to refresh anything a keyword page returned — and a page is increasingly parts you already hold as a shelf fills — so "Import new parts" spent rate-limited calls redoing sync's writes and reported them as `updated`. Two invariants now: **`synced` is 0 on EVERY import run** (assert it — if it moves, import is doing sync's job again), and a part this supplier already lists gets NO event and NO write, counted as `already listed` in the finished detail beside `already elsewhere` (detail only, deliberately not a wire event: a fully-covered page would emit 50 identical lines). **Do NOT "simplify" this to skip every existing part** — a part held from ANOTHER distributor must fall through and gain this supplier's offer, which is the one thing the whole multi-distributor pivot is for and which sync can never reach. That first offer is `listing_added`, NOT `updated`: 45,000 parts have no Mouser listing, so mislabelling it was most of what made the button look broken. Guard: `test_part_feed.py::TestImportDoesNotDoSyncsJob` (6) + `syncStream.test.ts`. Live console = `SyncConsole` (mode prop); persistence via `services/activity.record_stream_event` — created→`part_imported`, run labels stored as `import_*` for import runs (WIRE kinds never change); not_found/no_data transient. Nightly `feed-import` compose service honors `supplier_feeds.auto_import_enabled` (per-supplier toggle, PATCH 409s enable without provider+key; disable always allowed), budget `FEED_IMPORT_CALL_BUDGET=850` at `FEED_IMPORT_HOUR_UTC=6`; quota wall (Mouser 403 = FeedFatalError) stops the night via the `sync_error` event; ~1,000 calls/day tier is shared with daytime clicks — documented, not enforced. After big imports: regen `frontend/seo-manifest.json` + `--frontend` deploy or new part pages serve the generic shell. Runbook: `docs/part-import-runbook.md`.

- **PART IDENTITY is `UNIQUE(manufacturer_id, upper(sku))` (2026-08-23)** — one home, `app/services/part_identity.py`; every create path goes through `get_or_create_part` (3 importer sites + `POST /parts/` + `/batch`, the last two of which previously did NO existence check at all). **NEVER "improve" the key by stripping punctuation**: the decimal point is load-bearing (`1.5SMC6.8AHM3` is a 6.8V TVS diode, `1.5SMC68AHM3` is 68V; `CHD15MF-2.5` is 2.5ft, `-25` is 25ft). Measured on prod: case-folding collides on 6 groups, all 6 real duplicates; punctuation-stripping collides on 97, mostly distinct products. `test_part_identity.py` pins those exact part numbers. The manufacturer half is equally load-bearing — 49 MPN pairs span different makers (Desco taper tap vs Simpson panel meter). Feed-created parts now resolve manufacturer through canon AT WRITE TIME (they used to be born NULL and wait for the next container start's seed backfill — 3,229 such rows on prod); `_adopt_unlinked` claims a legacy NULL row instead of duplicating beside it.

- **Migration 041 (the identity cleanup) — what it does and what it deliberately does NOT.** Dry-run against live prod 2026-08-23 (`BEGIN … ROLLBACK`): parts 175,065→175,059 (−6), listings 212,187→212,166 (−21), duplicate groups 6→0, orphans 0, both constraints reject their probe insert. Four things worth knowing before touching it: (1) **merging parts MANUFACTURES the listing duplicate the same migration forbids** — the 6 groups collide on 21 (survivor, supplier) pairs, so the merge drops the stale side (freshest `last_updated` wins) and its price breaks BEFORE the constraint is added; skip that and the migration fails at the last step. (2) **Survivor = oldest `created_at`, but every field it lacks is COALESCEd from the loser** — two groups carry their only product photo on the NEWER row (a 2026-08 feed import with 1 listing) while the older row holds 10-12 listings, so a plain delete silently destroys two photos. (3) **No URL dies and no redirect is needed** — the duplicates differ only in capitalisation and `slug` derives from the lowercased sku, so both rows in every group already share a slug. But the two rows sit in DIFFERENT categories (that IS what created them), so the part disappears from one category page; `parts.category_id` is single-valued and they are one part. **Which one it keeps is an editorial decision, not insertion order** — `CATEGORY_PREFERENCE` in the migration names the intended home per MPN and outranks oldest-wins (keyed on `(MPN, sub_slug)`, never row id, so the same list is correct in every environment; unlisted groups still fall back to oldest). Decided from the rows' own descriptions: the five Nordic parts self-describe as "Bluetooth 5.x SoC" so they go to RF & Wireless ICs (`bluetooth` ×4, `rf-transceivers` for the nRF52833, whose description literally says "2.4GHz transceiver") — which also carries Nordic's official `nRF…` casing and the richer descriptions; the SiTime part goes the OTHER way to `oscillators` under Clock & Timing ICs, because `crystals-and-oscillators` sits under **Passive Components** and a MEMS oscillator is an active IC. Its two rows disagree on a real spec (20ppm vs 100ppm) and the merge keeps 20ppm — flagged, not adjudicated. **The decision has TWO homes and both were needed**: the migration fixes the six rows that exist on prod once, but `--reseed` TRUNCATEs parts while 041 stays applied and never re-merges, so the catalog JSON is the DURABLE authority — and it disagreed, listing four of the five Nordic parts in BOTH `microcontrollers-processors.json` and `rf-wireless-ics.json` while `_seed_real_catalog` reads `sorted(glob("*.json"))`, so `microcontrollers-…` won on every fresh database and reinstated exactly what the preference exists to correct. The duplicate entries were deleted (and the nRF52833, whose only home was `32bit-mcus`, moved to `rf-wireless-ics/rf-transceivers`). Guard: `test_the_catalog_json_agrees_with_the_preference`. (4) The listing constraint is built as `CREATE UNIQUE INDEX` then `ALTER TABLE … ADD CONSTRAINT … UNIQUE USING INDEX`, NOT the one-step `ADD CONSTRAINT UNIQUE (…)`: the one-step form builds its index under ACCESS EXCLUSIVE — which blocks READERS — and alembic's single transaction then holds that lock through every later statement and the commit, while the `feed-import` container is writing `part_listings` concurrently. (4) **`manufacturer_id` stays NULLABLE** — alembic runs BEFORE seed, prod has 3,229 unlinked rows at that moment, and resolving them needs `canon()`, which migrations cannot import (no migration in this repo imports app code). `seed_manufacturers` steps 2-5 drain every one of them on the next container start using the real canon(), so `SET NOT NULL` is a LATER migration that just asserts the column is clean. Excluding NULLs from the merge is correctness, not tidiness: Postgres GROUP BY treats NULLs as EQUAL, so an unguarded merge folds every unlinked row sharing an MPN into one product.

- **The suite can now test Postgres — `tests/pg_harness.py` (2026-08-23)** — everything else runs SQLite via `Base.metadata.create_all`, which structurally cannot test a data migration or an advisory lock, so both had shipped with zero automated proof. `test_migration_041_merge.py` executes the migration's **real `upgrade()`** (via `MigrationContext.configure(conn)` + `Operations.context(ctx)` — pass the CONTEXT, not `Operations(ctx)`) against the local Postgres inside a transaction it always rolls back, over the full ~175k-row catalog, so there is no second transcription of the SQL to drift and the index builds are exercised at production volume (whole file: 1.7s). Expose migration SQL as a module constant when a test needs to re-run it (041's `MERGE_DUPLICATE_PARTS` proves idempotency). Both harness files skip cleanly when the stack is down and REFUSE a non-local host. Temp tables in a migration need `DROP TABLE IF EXISTS` for ALL of them at the top, or the idempotency re-run dies on `DuplicateTable` (caught by the test, not by review).

- **Concurrency reality: prod runs `--workers 1`** (verified on the box; `API_WORKERS` is not in prod `.env`), and the api container writes parts concurrently with the `feed-import` container. **The connection pool is the untouched default 5+10=15, and that is FINE — the earlier "a feed thread holds a connection for the run's LIFE, so ~15 concurrent feeds kills the site" claim was WRONG, measured 2026-08-23.** A Session returns its connection to the pool at every `commit()` and the importer commits per part; `provider.search()` returns a fully-materialised `list`, so the HTTP call completes before any connection is taken. Measured: DB-held time is **2.2 ms/part** against ~8-16 ms of wall-clock, i.e. a run occupies a connection **12-22%** of the time → the pool saturates at **~70-124 concurrent runs**, not 15. Don't resize the pool without a measurement that contradicts this. (Reproduce: `engine.pool.checkedout()` around a commit, and time N part cycles.) **That headroom is conditional on nothing holding a pooled connection for a run's LIFETIME — and the feed lock nearly did.** `supplier_feed_lock` needs a connection for the whole run (advisory locks are per-connection); taken from the app engine it re-created the 15-run ceiling exactly, measured `checkedout=1` for the hold. It uses its own `NullPool` + AUTOCOMMIT engine for that reason. Any future long-held connection must do the same. Guard: `test_feed_lock.py::TestTheLockDoesNotCompeteWithHttpTraffic` (assert against a REAL Postgres engine — under pytest `app.db.session.engine` is SQLite, where the lock no-ops and the assertion passes without measuring anything).

- **Write waste — FIXED 2026-08-23, keep it fixed.** `_stamp_feed_facts` used to set `lifecycle_verified_at` OUTSIDE its `!=` guard, so every part a feed touched was UPDATEd even when nothing changed: 139,056 updates at **2.8% HOT** (97% rewrote all 8 indexes), ~3 GB WAL per Mouser import. It is now inside the guard, so the column means "when a feed established the lifecycle this row currently claims" — safe because **no consumer reads the VALUE** (`bom_match` asks `is not None` plus a nulls-last tie-break). Guard: `test_feed_part_facts.py::TestUnchangedRowsAreNotRewritten`. Also fixed: `part_listings.supplier_id` is indexed (migration 042 — it was a `Parallel Seq Scan` over 212,187 rows, 30.7 ms, on the supplier detail page; 041's `UNIQUE(part_id, supplier_id)` does NOT cover it, a composite can't serve its second column alone), and `_upsert_listing` passes `noload(PartListing.price_breaks)`. Guard: `test_feed_query_budget.py`. STILL OPEN: `price_breaks_pkey` is 40MB with **zero index scans ever** — but it is the PK and SQLAlchemy cannot map a table without one, so the only real fix is a composite PK on `(listing_id, min_quantity)`, not a drop.

- **Price ladders are RECONCILED rung-by-rung, never replaced (2026-08-24)** — `_upsert_listing` used to `DELETE WHERE listing_id = ?` and re-INSERT every break on every pass. `pg_stat_user_tables` on `price_breaks` was the whole diagnosis: **846,167 live rows carrying 2,760,938 inserts and 2,080,759 deletes, and `n_tup_upd = 0`** — 5.7 row-ops per row that exists, and not one row ever updated because nothing ever tried. That stat line is the fingerprint of a replace-instead-of-reconcile write path; look for it first on any churning table. `_sync_price_breaks` now diffs on `min_quantity` (the natural key inside a listing): measured over **2,000 real Mouser listings / 10,642 rungs whose prices had not moved, it writes ZERO rows** (extrapolated: a full no-change Mouser sweep goes 828,673 row-ops → 0), trading 12,642 write statements for 2,000 targeted reads at 0.73 ms/listing. A single moved rung is `n_tup_upd +1, n_tup_hot_upd +1, ins +0, del +0`. **The rounding is load-bearing, not tidiness**: real DigiKey payloads quote five decimals (`0.03909`) into a `Numeric(10,4)` that stores `0.0391`, so comparing raw feed precision to a stored value differs on EVERY pass — a diff without `_storable_price` would swap delete+insert for a permanent UPDATE and look fixed. 136,698 live rows already use that 4th decimal. The SAME trap applies to `listing.unit_price` one level up (4 indexes, plus an `updated_at` bump that made untouched rows indistinguishable to anything watermark-based — this is what blocked an incremental `circuits pull --catalog`), so it rounds through the same helper. `_PRICE_SCALE` reads `PriceBreak.__table__.c.unit_price.type.scale` rather than hardcoding 4. The diff also collapses duplicate `(listing_id, min_quantity)` rows — nothing in the schema forbids them (separate indexes only, 0 on prod today), and updating one copy would strand the other forever. Guards: `test_feed_query_budget.py` (SQLite, the SQL emitted) + **`test_price_break_writes_pg.py`** (Postgres, what the SQL DOES — `ctid` identity proves "nothing was written" in a way SQLite structurally cannot, and it asserts `unit_price` stays unindexed because that is what keeps the reprice HOT-eligible). Both mutation-verified against the old behaviour.

- **OPEN, and newly urgent: `price_stale` on the BOM tool is measuring the wrong thing (found 2026-08-24)** — `bom_match._offers_for_part` sets `price_stale = last_updated < now - 30 days`, but **`part_listings.last_updated` has `default=` and NO `onupdate=`**, so it is stamped once at INSERT and nothing has ever bumped it. It means "created", not "price confirmed". Measured on the local catalog: of 130,728 Mouser listings only 1,352 currently render stale — purely because most were created recently — while every one of the ~4,200 genuinely unrefreshed 2026-06-03 rows correctly does. As Mouser listings age past 30 days they become indistinguishable from the unrefreshed ones **even though the feed confirms them nightly**, which is exactly the credibility problem the multi-distributor pivot exists to fix. Pre-existing, NOT caused by the reconciler — but the reconciler removes the last incidental write that could ever have carried a freshness signal, so it now needs an explicit home. **Do NOT "fix" it by stamping `last_updated` on every confirming pass** — that is 130,728 UPDATEs on a 4-index table per sweep, i.e. re-creating the churn that was just removed, and it is the same mistake `lifecycle_verified_at` made. Freshness is a property of the FEED, not of each row: `supplier_feeds.last_synced_at` already records it at one row per supplier. Changing what the public BOM tool tells buyers is a product decision, so it is filed here rather than done silently.
